Package: org.apache.grails.datamapping.core.querytail

[Groovy] Class QueryTailCapture

    • org.apache.grails.datamapping.core.querytail.QueryTailCapture
    • All Implemented Interfaces and Traits:
      java.io.Closeable
      @groovy.transform.CompileStatic
@groovy.util.logging.Slf4j
class QueryTailCapture
extends java.lang.Object
implements java.io.Closeable

      Writes the statements an application runs to the capture file the query-tail command tails. Each session factory, Neo4j driver, MongoDB client or simple datastore that captures opens its own capture and closes it when it closes; the captures of one file share it, so every data source of an application writes to the one file. The file is truncated when the first capture opens it, so it holds the statements of the current run only, and its first line names that run. It is closed when the last capture closes, and opened afresh by the next one. Each statement is written whole and at once, so that the command sees it as soon as it is recorded.

      JVMs that run at the same time with capture enabled, such as the parallel forks of a test task, share the file: a lock file beside it tells the first to start, which truncates the file and names the run, from the others, which append to that run without truncating it and number their requests apart, so that the command reads one run from all of them. The lock file is beside the file itself, whatever symbolic link a JVM names it by, so JVMs that name it differently still share its run. A build can name the run with RUN_PROPERTY, as the Grails Gradle plugin does for the test tasks of one invocation: a capture that finds the file headed by that run appends to it, so that the datastores a test JVM opens and closes one after another, and the test tasks that run one after another, all add to the one run.

      Two applications that run in one JVM, each with this class of its own, as two web applications of one servlet container do, cannot share a file: the locks of a file are held by the process, so neither could hold one apart from the other, nor keep the other's when it closes the file. The capture that finds the other application's lock on the file is reported and stopped before it writes anything, and the other goes on; each application is given a file of its own with QueryTailSettings.SETTING_FILE.

      Recording never fails the statement it records: a statement that cannot be written, or whose request cannot be told, is left out, and a capture that has stopped does no work at all. A file whose write fails is written no more until the next capture opened on it opens it again, for every capture of it, and appends to the run it was writing while the file still holds that run, so that what was recorded before the failure is kept. Opening never fails what opens it either: a file that cannot be created is reported, and its capture has stopped before it records anything, and one whose lock file another JVM keeps from being had for STARTING_WAIT, as a JVM paused while it starts a capture does, is reported and stopped likewise, so a setting meant to diagnose an application never keeps it from starting, nor blocks the statements it runs.

      A process that captures can be checkpointed with CRaC, which refuses to checkpoint one that holds a file open: when org.crac is on the classpath, as checkpointing with Spring requires, every capture file is closed before the checkpoint, along with its lock file, and opened again after the restore as a capture opening it first would open it, so that a restored application starts a run of its own unless another JVM is writing one. A capture opened while the process is checkpointed opens its file with the others, and a statement run meanwhile is not recorded.

      A statement is recorded without its values: QueryTailRedactor replaces its literals and drops its comments before it is written, in the syntax of the database it runs on. A capture keeps what the REMEMBERED_REDACTIONS statements it recorded most recently were redacted to, letting go of the one recorded least recently to keep another, so that a statement run again, as the statements an application generates with parameters for its values are, is not read again on the thread that runs it, which a syntax that reads it every way it may be read, as that of a database that is not known does, would read it many times. A statement that is not text, such as a MongoDB command, or that is built without values, as the operations of the simple datastore are, has its values taken out by whoever records it, through recordRedacted.

      A capture is only opened when QueryTailSettings.SETTING_ENABLED is set; an application started without it never reaches this class.

        • void recordRedacted(java.lang.String dataSource, java.util.function.Supplier<java.lang.String> statement)

          Records a statement that is about to run on the current thread and that holds no value any more: a MongoDB command, which is a document rather than text, is redacted field by field by the listener that records it, and the simple datastore builds its statements from the query, without a value.
